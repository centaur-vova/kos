# SOLUTION — Ключевые решения

## Стек: почему PHP + Swoole

- **PHP** — основной язык проекта, не надо тащить второй стек.
- **Swoole** — корутины, event loop, shared memory. Даёт производительность Go/Node без смены языка.
- **Swoole\Table** — идемпотентность и блокировки в shared memory, без Redis для одного инстанса.
- **Минусы**: сложнее отладка асинхронного кода, меньше готовых решений, не все разработчики знакомы со Swoole. Для прода — учитывать в онбординге.

## Почему PostgreSQL

- ACID — критично для денег.
- `SELECT ... FOR UPDATE` — пессимистические блокировки.
- Уникальные constraint'ы — защита от дублей на уровне БД.
- Частичные индексы — для витрины каталога.
- JSONB — для event sourcing.

Пул соединений — `Swoole\Database\PDOPool` (25 соединений в MVP). В проде — тюнинг размера, мониторинг утечек, graceful shutdown.

## Почему Swoole\Table вместо Redis

- Нет сетевого оверхеда — shared memory в ядре Linux.
- Быстрее — не нужна сериализация и TCP.
- Проще — не нужен отдельный контейнер.
- Достаточно для одного инстанса.

При горизонтальном масштабировании → Redis для multi-node синхронизации.

## Архитектура

Монолит с модулями:

- **Controller** — HTTP-слой
- **Service** — бизнес-логика
- **Storage** — идемпотентность, блокировки
- **DTO** — входные данные
- **Enum** — статусы, события

Паттерны:

- DI через PHP-DI
- `LockerInterface` / `SwooleTableLocker` — блокировки на заказ
- Anti-Corruption Layer — `PaymentWebhook::fromArray()` изолирует внешний формат платёжки
- Saga Pattern — `DeliveryService` с параллельной выдачей и компенсациями
- Event Sourcing — append-only журнал в `order_events`

## Идемпотентность платежей

**Проблема**: платёжка шлёт вебхук несколько раз (at-least-once delivery).

**Решение** — двойная защита:

1. `Swoole\Table` — быстрый кэш обработанных `event_id`, снижает нагрузку на БД при повторах.
2. Уникальный constraint `payments.event_id` — гарантия exactly-once на уровне БД.

**Оговорка.** `SwooleTableLocker::acquire` и `SwooleTableStorage::set` не атомарны: между `has()` и `set()` есть окно, поэтому при жёсткой конкуренции кэш может пропустить дубль. Реальная защита от гонок — constraint'ы в БД. В проде — Redis с `SET NX EX` или `Swoole\Table::incr` с TTL-колонкой.

## Exactly-once под гонками

**Проблема**: 50 параллельных вебхуков на один заказ.

**Решение**:

- Оптимистическая блокировка: `WHERE status = 'created'` + `rowCount()`.
- Только один вебхук переводит заказ `created → paid`.
- Остальные получают `processed_by_other`.

## Таймаут провайдера ≠ отказ

**Проблема**: поставщик мог выдать код, но ответ не дошёл.

**Решение**:

- Детерминированный `request_id` для каждой попытки.
- Поставщик кэширует выданный код по `request_id` — повтор возвращает тот же код.
- `order_items.provider_request_id` — уникальный constraint.

## Fallback A → B

**Проблема**: провайдер A недоступен или вернул грязный код.

**Решение**: цепочка провайдеров через `Options::getNextProvider()`. Если A падает — идём к B с новым `request_id`.

## Мультитоварный заказ (Saga Pattern)

**Проблема**: несколько товаров, часть может не выдаться.

**Решение**:

- Параллельная выдача через `Swoole\Coroutine\Barrier`.
- Компенсации: рефанд за неуспешные позиции.
- Инвариант: `оплачено = выдано + возвращено`.
- Идемпотентность через `refunds.order_item_id UNIQUE`.

## Защита от фрода

**Проблема**: поставщик может прислать дубль, чужой код или HTTP 500 при выданном коде.

**Решение**:

- Уникальность кода — `order_items.delivered_code UNIQUE`.
- Валидация маски — `key: XXXX-XXXX-XXXX`, `topup/giftcard: TOPUP-`.
- Детерминированный `request_id` — повтор не создаёт дубль.
- Fallback — грязный код → следующий провайдер.
- Логирование — каждая аномалия с кодом и провайдером.

## Event Sourcing

**Проблема**: восстановить состояние заказа и денег на любой момент.

**Решение**:

- Append-only журнал `order_events` с запретом `UPDATE/DELETE` (PostgreSQL rules).
- Проекция состояния — `getStateAt()` накатывает события до даты.
- Финансовый отчёт — агрегация `amount_cents` из событий за период.
- Сходимость — итоги считаются из той же истории, что и состояние.

## Сверка и восстановление

- `GET /reconciliation` — зависшие заказы («оплачен, но не выдан» / «выдан, но не оплачен»).
- `POST /recovery` — ручной запуск восстановления.
- `RecoveryService` — фоновая задача через `Swoole\Timer`.
- Индекс `idx_orders_stuck_states` для быстрого поиска.

**Почему не очередь.** В проде recovery, выдача и рефанды шли бы через очередь (NATS/RabbitMQ/Redis Streams) с воркерами per-provider и rate limit — это дало бы естественную идемпотентность, повторы с бэкоффом и горизонтальное масштабирование. В тестовом задании очередь осознанно не тянется: нет Redis/RabbitMQ в стеке, ТЗ не требует мультиинстанса, а `SwooleTableLocker` + идемпотентность в БД + `Swoole\Timer` покрывают все сценарии для одного процесса. При переходе в прод `RecoveryService` превращается в `publish(order_id)`, `DeliveryService` — в воркер.

## Каталог под нагрузкой

- Частичный индекс `(type, price_cents) WHERE stock > reserved`.
- На десятках тысяч SKU PostgreSQL выбирает Seq Scan — он быстрее Index Scan из-за низкой селективности.
- На сотнях тысяч SKU — покрывающий индекс и Index Scan.
- Пагинация через `LIMIT/OFFSET` в API (в проде — keyset pagination).

## Известные ограничения MVP

- **Task 3** (лимит поставщика) — бонусная, не реализована.
- **Event Bus** — события пишутся напрямую, без outbox pattern.
- **Деньги как float** — в проде moneyphp/money.
- **Repository pattern** — SQL местами в сервисах, в проде вынес бы.
- **Гонка ретраев** — в проде `FOR UPDATE` на заказе вокруг всего цикла выдачи.
- **Лок в памяти не атомарен.** `SwooleTableLocker` использует `has()` + `set()`, между ними есть окно для гонки. Реальная защита — constraint'ы в БД, в проде — Redis `SET NX EX`.

## Что нужно для прода

- **Очереди** — NATS/RabbitMQ для фоновых задач (recovery, выдача, рефанды).
- **Rate limiting** — Redis для лимитов поставщиков (Task 3).
- **Outbox pattern** — гарантия доставки событий.
- **Money pattern** — moneyphp/money.
- **Repository pattern** — вынести SQL из сервисов.
- **Мониторинг** — Prometheus + Grafana, алерты.
- **Трейсинг** — OpenTelemetry + Jaeger.
- **CI/CD** — GitHub Actions (уже есть).

## Масштабирование

- **Каталог**: кэш в Redis/Swoole Table + инвалидация по TTL.
- **API**: несколько инстансов + балансировщик.
- **PostgreSQL**: реплики для чтения.
- **Swoole Table → Redis** для multi-node синхронизации.
- **Очереди**: NATS/RabbitMQ для фоновых задач.
- **Мониторинг**: Prometheus + Grafana.
