# SOLUTION — Ключевые решения

## Почему Swoole

### Плюсы

- **Корутины** — нативная асинхронность, не блокирует event loop
- **Меньше памяти** — воркеры вместо процессов, как в PHP-FPM
- **Swoole Table** — shared memory для идемпотентности без Redis
- **Высокий RPS** — под нагрузкой быстрее синхронного PHP

### Минусы

- **Сложность** — не все разработчики знают Swoole
- **Отладка** — труднее дебажить асинхронный код
- **Экосистема** — меньше готовых решений

### Почему не Node.js/Go

- PHP — основной стек
- Swoole даёт производительность Go/Node без смены языка
- Меньше зависимостей, чем Symfony/Laravel

## Почему PostgreSQL

- ACID — критично для денег
- SELECT ... FOR UPDATE — пессимистические блокировки
- Уникальные constraint — защита от дублей
- Частичные индексы — для витрины
- JSONB — для event sourcing

## Пул соединений

В MVP — Swoole\Database\PDOPool с пулом на 25 соединений.

**В проде** — тюнинг размера пула, мониторинг утечек, graceful shutdown.

## Почему Swoole Table вместо Redis

- **Нет сетевого оверхеда** — shared memory в ядре Linux
- **Быстрее** — не нужно TCP/IP, сериализация
- **Проще** — не нужен отдельный контейнер
- **Достаточно** — для одного инстанса

В проде при горизонтальном масштабировании — Redis для multi-node синхронизации.

## Архитектура

Монолит с модулями:

- Controller — HTTP слой
- Service — бизнес-логика
- Storage — идемпотентность
- DTO — входные данные
- Enum — статусы, события

Паттерны:

- DI через PHP-DI
- LockService для блокировок
- Anti-Corruption Layer — PaymentWebhook::fromArray() изолирует внешний формат
- Saga Pattern — DeliveryService с параллельной выдачей и компенсациями
- Event Sourcing — append-only журнал в order_events

## Идемпотентность платежей

**Проблема**: платёжная система может прислать вебхук несколько раз (at-least-once delivery).

**Решение**: двойная защита:

1. **Swoole Table** — быстрый барьер в памяти
2. **Уникальный constraint** payments.event_id — гарантия на уровне БД

При гонке: первый вебхук пройдёт, остальные получат UNIQUE_VIOLATION и вернут already_processed_race.

## Exactly-once под гонками

**Проблема**: 50 параллельных вебхуков на один заказ.

**Решение**:

- Оптимистическая блокировка через WHERE status = 'created' + rowCount()
- Только один вебхук переведёт заказ из created в paid
- Остальные получат processed_by_other

## Таймаут провайдера ≠ отказ

**Проблема**: поставщик может выдать код, но ответ не дойдёт (таймаут).

**Решение**:

- Детерминированный request_id для каждой попытки
- Поставщик кэширует выданный код по request_id
- Повтор с тем же request_id возвращает тот же код
- order_items.provider_request_id — уникальный constraint

## Fallback A → B

**Проблема**: провайдер A недоступен или вернул грязный код.

**Решение**: цепочка провайдеров через Options::getNextProvider(). Если A падает — идём к B с новым request_id.

## Мультитоварный заказ (Saga Pattern)

**Проблема**: несколько товаров, часть может не выдаться.

**Решение**:

- Параллельная выдача через Swoole\Coroutine\Barrier
- Компенсационные операции: рефанд за неуспешные позиции
- Баланс: оплачено = выдано + возвращено
- Идемпотентность через refunds.order_item_id UNIQUE

## Защита от фрода

**Проблема**: поставщик может прислать дубль, чужой код, или HTTP 500 при выданном коде.

**Решение**:

- **Уникальность кода** — order_items.delivered_code UNIQUE
- **Валидация маски** — key: XXXX-XXXX-XXXX, topup/giftcard: TOPUP-
- **Детерминированный request_id** — повтор не создает дубль
- **Fallback** — грязный код → следующий провайдер
- **Логирование** — каждая аномалия с кодом и провайдером

## Event Sourcing

**Проблема**: восстановить состояние заказа на любой момент времени.

**Решение**:

- **Append-only журнал** — order_events с запретом UPDATE/DELETE (PostgreSQL rules)
- **Проекция состояния** — getStateAt() накатывает события до даты
- **Финансовый отчет** — агрегация amount_cents из событий за период
- **Сходимость** — итоги считаются из той же истории, что и состояние

## Сверка и восстановление

- GET /reconciliation — показывает зависшие заказы
- POST /recovery — ручной запуск восстановления
- RecoveryService — фоновая задача через Swoole\Timer
- Индексы idx_orders_stuck_states для быстрого поиска

## Каталог под нагрузкой

- Составной частичный индекс (type, price_cents) WHERE stock > reserved
- При 10k SKU PostgreSQL выбирает Seq Scan (2.7ms) — оптимально
- При 100k+ SKU — Index Scan через покрывающий индекс
- Пагинация через LIMIT/OFFSET в API

## Известные ограничения MVP

- **Задача 3** (лимит поставщика) — бонусная, не реализована
- **Event Bus** — события пишутся напрямую, без outbox pattern
- **Rate limiting** — для очередей нужен Redis
- **Деньги как float** — в проде moneyphp/money
- **Repository pattern** — SQL в сервисах, в проде вынес бы
- **Гонка ретраев** — в проде FOR UPDATE на заказе вокруг всего цикла
