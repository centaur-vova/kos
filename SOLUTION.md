# SOLUTION — Ключевые решения

## Почему Swoole

### Плюсы

- **Корутины** — нативная асинхронность, не блокирует event loop
- **Меньше памяти** — воркеры вместо процессов, как в PHP-FPM
- **Swoole Table** — shared memory для идемпотентности без Redis
- **Высокий RPS** — под нагрузкой быстрее синхронного PHP

### Минусы

- **Сложность** — не все разработчики знают Swoole
- **Отладка** — труднее дебажить асинхронный код
- **Экосистема** — меньше готовых решений, чем у Laravel

### Почему не Node.js/Go

- PHP — основной стек
- Swoole даёт производительность Go/Node без смены языка
- Меньше зависимостей, чем Symfony/Laravel

## Почему PostgreSQL

- ACID — критично для денег
- `SELECT ... FOR UPDATE` — пессимистические блокировки
- Уникальные constraint — защита от дублей
- Частичные индексы — для витрины
- Стабильность и проверенность

## Пул соединений

В MVP — `new PDO` на каждый запрос (через фабрику). Для тестового достаточно.

**В проде** — `Swoole\ConnectionPool`:

- Один пул на воркер
- Переиспользование сокетов
- Контроль `max_connections`
- Защита от исчерпания портов

## Почему Swoole Table вместо Redis

- **Нет сетевого оверхеда** — shared memory в ядре Linux
- **Быстрее** — не нужно TCP/IP, сериализация
- **Проще** — не нужен отдельный контейнер/сервис
- **Достаточно** — для одного инстанса Swoole Table перекрывает потребности

В проде при горизонтальном масштабировании — Redis для multi-node синхронизации.

## Архитектура

Монолит с модулями:

- `Controller` — HTTP слой
- `Service` — бизнес-логика
- `Storage` — идемпотентность
- `DTO` — входные данные
- `Enum` — статусы

Паттерны:

- DI через PHP-DI
- LockService для блокировок
- Anti-Corruption Layer (ACL) — PaymentWebhook::fromArray() изолирует внешний формат от внутреннего
- Repository pattern не использовали для MVP (в проде — вынес бы SQL из сервисов)

## Почему не все DTO

- Входные данные — DTO (PaymentWebhook)
- Выходные — массивы, для MVP читаемо
- В проде — типизированные DTO для ответов

## Идемпотентность платежей

**Проблема**: платёжная система может прислать вебхук несколько раз (at-least-once delivery).

**Решение**: двойная защита:

1. **Swoole Table** (shared memory) — быстрый барьер в памяти
2. **Уникальный constraint** `payments.event_id` — гарантия на уровне БД

При гонке: первый вебхук пройдёт, остальные получат `UNIQUE_VIOLATION` и вернут `already_processed_race`.

## Exactly-once под гонками

**Проблема**: 50 параллельных вебхуков на один заказ.

**Решение**:

- Оптимистическая блокировка через `WHERE status = 'created'` + `rowCount()`
- Только один вебхук переведёт заказ из `created` в `paid`
- Остальные получат `processed_by_other`

## Таймаут провайдера ≠ отказ

**Проблема**: поставщик может выдать код, но ответ не дойдёт (таймаут).

**Решение**:

- Детерминированный `request_id` для каждой попытки
- Поставщик кэширует выданный код по `request_id`
- Повтор с тем же `request_id` возвращает тот же код
- `deliveries.request_id` — уникальный constraint

## Fallback A → B

**Проблема**: провайдер A недоступен.

**Решение**: цепочка провайдеров через `Options::getNextProvider()`. Если A падает — идём к B с новым `request_id`.

## Сверка и восстановление

- `GET /reconciliation` — показывает зависшие заказы
- `RecoveryService` — фоновая задача через `Swoole\Timer`, перезапускает выдачу
- Индексы `idx_orders_stuck_states` для быстрого поиска

## Каталог под нагрузкой

- Составной частичный индекс `(type, price) WHERE stock > reserved`
- Для 12 записей Seq Scan быстрее, для тысяч — Index Scan
- `idx_products_catalog_available` — один индекс для фильтрации и сортировки

## Известные ограничения MVP

- **PDO без пула** — в проде `Swoole\ConnectionPool`
- **Синхронный логгер** — в проде асинхронный
- **Деньги как float** — в проде `moneyphp/money`
- **Нет Repository pattern** — в проде вынес бы SQL из сервисов
- **Гонка ретраев** — в проде `FOR UPDATE` на заказе вокруг всего цикла ретраев
- **Возврат ключа вне транзакции** — в проде транзакция вокруг `completeOrder`

## Что не стал делать

- **Swagger/OpenAPI** — перебор для MVP
- **Graceful shutdown** — не критично для тестового
- **Отдельный Repository слой** — для MVP сервисы достаточны
- **Money pattern** — float для демо, в проде — moneyphp/money
- **Больше DTO** — входные DTO есть, выходные — массивы. В проде — типизированные DTO для ответов
- **Очереди** — для MVP корутины достаточны, в проде — NATS/RabbitMQ

## Почему свой роутер

- **Простота** — 50 строк вместо фреймворка
- **Контроль** — знаю, как парсятся маршруты
- **Производительность** — нет лишнего оверхеда
- **Зависимости** — не тащу FastRoute/Symfony Router

В проде — заменил бы на FastRoute или Symfony Router, если бы маршрутов стало много.

## Что нужно для прода

- **Мониторинг** — Prometheus + Grafana, алерты
- **Трейсинг** — OpenTelemetry + Jaeger
- **Очереди** — NATS/RabbitMQ для фоновых задач
- **Connection Pool** — Swoole\ConnectionPool для БД
- **Money pattern** — moneyphp/money
- **Repository pattern** — SQL из сервисов
- **Graceful shutdown** — корректное завершение
- **Rate limiting** — защита от DDoS
- **Аутентификация** — JWT/API keys
- **Версионирование API** — /api/v1/...
- **CI/CD** — GitHub Actions/GitLab CI

## Масштабирование

- Горизонтально: несколько инстансов API + балансировщик
- PostgreSQL: реплики для чтения
- Swoole Table → Redis для multi-node
- Очереди: NATS/RabbitMQ для фоновых задач
- Мониторинг: Prometheus + Grafana
